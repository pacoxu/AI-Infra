# LWS v0.11.0：KEP-666 原生 Gang Scheduling 落地

[LeaderWorkerSet v0.11.0](https://github.com/kubernetes-sigs/lws/releases/tag/v0.11.0)
于 **2026-09-23** 发布。本篇按发布说明与上游仓库内容整理，重点介绍本版本合入的
[KEP-666](https://github.com/kubernetes-sigs/lws/blob/main/keps/666-gang-scheduling-in-lws/README.md)：
把 LWS 接到 Kubernetes 1.37 的 Workload-Aware Scheduling（WAS）。

## 为什么需要它

分布式推理里，一个 replica 只有 leader 和 workers 一起跑起来才有用。按 Pod
独立调度会出现两类常见浪费：

- 部分成员占住加速器，整组却起不来
- 多个不完整 replica 互相卡住，谁也凑不齐

LWS 早先通过 [KEP-407](https://github.com/kubernetes-sigs/lws/tree/main/keps/407-gang-scheduling)
对接第三方 gang scheduler（如 Volcano）。Kubernetes 1.37 提供了上游
`Workload` / `PodGroup` 契约与 `workloadbuilder`。KEP-666 的目标是复用这套 API，
而不是再维护一套并行的调度语义；LWS 特有的部分，主要是把调度意图映射到
LWS / replica / leader-worker 这层结构。

## Phase 1 交付了什么

v0.11.0 落地的是 **Phase 1（Alpha）**：

| 项 | 内容 |
| --- | --- |
| 用户 API | alpha 字段 `spec.scheduling`（创建后不可变） |
| Feature gate | `WorkloadAwareScheduling`，默认关闭 |
| Provider | `gangSchedulingManagement.schedulerProvider`；`kubernetes` 走上游 WAS |
| 对象形态 | 一个 `scheduling.k8s.io/v1beta1` Workload + **扁平** PodGroup |
| 默认行为 | `spec.scheduling: {}` → 每个 replica 一个 PodGroup，`gang.minCount = size` |
| 与旧路径关系 | 未设 `spec.scheduling` 时，保留 KEP-407 的 Volcano 行为 |

Phase 1 每次只允许 **一个活跃层级**（整 LWS、replica、或 leader/worker leaf）。
多层级 `CompositePodGroup` 留给 Phase 2，不在本版本范围。

默认 replica 模式大致是：

```text
LWS
├── Workload（LWS 拥有）
├── PodGroup "replica-0" ── leader 0 + workers 0
├── PodGroup "replica-1" ── leader 1 + workers 1
└── ...
```

扩缩 replica 时，已在跑的组不受影响；整组不够资源时一起 pending，而不是留下半组。

## 怎么用（最小示例）

来自 KEP 示例，省略与调度无关的模板细节：

```yaml
apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata:
  name: inference
spec:
  replicas: 4
  scheduling:
    replica:
      schedulingPolicy:
        gang: {}   # Phase 1：minCount 默认等于 size
      disruptionMode:
        all: {}
  leaderWorkerTemplate:
    size: 2
    # leaderTemplate / workerTemplate ...
```

开启后，controller 会编译出对应 Workload，再按 replica 创建 PodGroup；Pod 上由
LWS 写入 `spec.schedulingGroup.podGroupName`，指向该组。用户模板里不要预置
`schedulingGroup`。

使用 `kubernetes` provider 还需要集群侧打开 `GenericWorkload`（kube-apiserver、
kube-controller-manager、kube-scheduler）。缺少 API 时，admission 会拒绝带
`spec.scheduling` 的对象。

## 明确不做什么

KEP 写进 Non-Goals / Future 的边界，本版本也按此理解：

- 不在 LWS controller 里创建 DisaggregatedSet 所需的额外 role/slice 层
- 不支持 `startupPolicy: LeaderReady` 与「leader+worker 同一 gang」混用
- 不替代 Volcano queue 等 provider 专有配置
- 不实现 Kueue 入队；只暴露调度配置给上层集成
- Phase 2 的 CompositePodGroup、以及 DisaggregatedSet 作为 parent 的集成，后续再做

## v0.11.0 其他值得一眼的变化

发布说明里还有一批与 gang 无关、但同版本合入的工作，这里只列要点：

- DisaggregatedSet：status / Available·Progressing、虚拟 sub-role（KEP-960）、若干校验与 Service 归属修复
- `groupIdentity` Hash，以及 `groupReplacementPolicy` 序列化 hash group 替换
- 文档重组、vLLM / SGLang 示例刷新、Kueue topology 示例恢复
- Kubernetes 依赖升到 v1.37

社区同时把 **1,000 GitHub stars** 设成这个里程碑的目标。截至 **2026-10-09**，[kubernetes-sigs/lws](https://github.com/kubernetes-sigs/lws) 是 **858** star。

仓库：<https://github.com/kubernetes-sigs/lws>

这里的 v1.0.0 是**项目版本**。LeaderWorkerSet 的 CRD 已经是 `leaderworkerset.x-k8s.io/v1`，DisaggregatedSet 文档侧也是 `disaggregatedset.x-k8s.io/v1`。公告没有附变更清单，仓库里也还没有对应的 v1.0.0 release issue。本文前面的 KEP-666 / `WorkloadAwareScheduling` 在 v0.11 仍是默认关闭的 Alpha，上游 README 也仍把 gang scheduling 标成 API 可能变化；这次 1.0 公告没有把它们标成毕业。

安装文档已经按「即将升到 v1.0.0」写了一条迁移约束，来自 [Migrate pre-slices DisaggregatedSets before v1.0.0](https://lws.sigs.k8s.io/docs/installation/)：

- DisaggregatedSet 从 v0.9.0 开始提供，当时还没有 `slices`
- 对象如果是 v0.9.x 创建的，并且在 v0.10.x / v0.11.x 上还没完成过一次 template rollout，**不要直接升到 v1.0.0**
- 先装 v0.10.x 或 v0.11.x，再对每个受影响的 DisaggregatedSet 做完一次 rollout（例如改某个 role 的容器镜像）。这一步会换成带 slice-aware 名字和标签的 LeaderWorkerSet 与 Pod
- 已经在 v0.10 / v0.11 上滚过的，不需要再迁

升级前，下面这条命令不应有输出：

```shell
kubectl get leaderworkersets -A \
  -l 'disaggregatedset.x-k8s.io/name,!disaggregatedset.x-k8s.io/slice'
```

Helm 升级另外要注意：`helm upgrade` 不会带上新 CRD。DisaggregatedSet 有两份，`disaggregatedsets` 从 v0.9.0 起，`disaggregatedsetrolescalers` 从 v0.10.0 起。只应用前者时，`scaling.mode: External` 依赖的 `DisaggregatedSetRoleScaler` 创建不出来。按安装文档，升级前用 `kubectl apply --server-side` 把 chart 里的全部 CRD 铺上去。
